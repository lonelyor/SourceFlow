# SourceFlow 通用工程规则

更新日期：2026-06-03

本文件记录跨阶段、跨模块长期有效的工程规则。阶段设计写入 `plans/spec.md`，当前状态写入 `plans/state.md`，任务队列写入 `plans/todo.md`；本文件只放通用约束，不记录临时方案。

## 授权与最小范围

- 只围绕用户本轮明确授权的目标修改，不借机扩展需求、重构无关模块或调整无关文档。
- 修复 bug 时默认保持既有功能语义、接口、数据结构和安全边界不变；如必须改变，应先说明影响并等待确认。
- 每次改动必须保持最小必要 diff；能局部修补就局部修补，不能整文件重写。
- 修改前必须阅读相关实现、接口、调用链和计划文档；上下文不足时先搜索，不基于猜测修改。
- 不修改仓库根目录之外的文件，除非用户明确授权对应路径。

## 唯一真相源

- 配置、状态、协议字段、事件名、路径、错误码、默认值、阈值和公共函数只要被引用超过 2 次，就必须提炼为唯一真相源。
- 前后端共享语义必须有明确映射：后端模型、API schema、TypeScript 类型、UI 保存逻辑、i18n、搜索索引和测试应保持一致。
- 禁止在多个模块复制同一默认值、同一字段名或同一安全判断；应通过常量、类型、 helper 或集中配置读取。
- 安全规则、权限矩阵、批量阈值、路径边界和写入策略必须集中在明确模块内，不允许分散到 UI 分支里各自判断。
- 人写配置优先使用 YAML；机器读写和持久化状态优先使用 JSON，并保持字段名稳定。

## 归一化

- 所有外部输入进入业务逻辑前必须归一化：路径、ID、枚举、布尔值、数值范围、空字符串、列表去重和排序口径都应在边界层处理。
- 归一化后的数据必须成为后续流程唯一输入；业务模块不应反复处理原始输入。
- 路径必须归一化到允许根目录内，再进行读写、移动、删除或递归扫描；禁止接受 `..`、绝对路径和卷标路径越界。
- 配置读取必须补默认值、裁剪非法值并保持类型稳定；保存配置时不得把临时 UI 状态写入持久配置。
- 列表型状态应去重、稳定排序或保留明确顺序语义；批量操作必须有上限。
- 文本和文件内容统一按 UTF-8 处理；错误消息和日志不得泄露密钥、token、完整隐私内容或敏感路径。

## 幂等与事务

- 重复执行同一保存、同步、索引、迁移、初始化、清理或恢复操作，应得到相同结果，不应产生重复记录、重复 DOM、重复事件绑定或重复副作用。
- 状态变更必须尽量原子化：先校验、再预览、再提交；失败时保留原状态或进入可恢复状态。
- 写文件优先使用临时文件安全写入，避免先清空原文件；失败时应尽量保留原文件。
- 批量写入、事务和 AI patch 应支持逐项失败记录、回滚或人工审阅；禁止吞掉错误后提交部分不可追踪变更。
- 初始化和迁移逻辑必须可重复运行；已经存在的用户配置和用户状态不得被默认值覆盖。
- 事件监听、定时器、异步任务、网络请求和并发任务必须有取消、超时、资源释放和重复注册保护。

## 状态边界

- 模块内部状态应明确生命周期、所有权和释放方式；共享可变对象不得跨缓存、渲染、事务和索引流程复用。
- 缓存只能缓存不可变数据或明确复制后的数据；读取缓存时如会被调用方修改，必须返回独立副本。
- UI 临时状态、会话状态、用户持久配置和机器审计日志必须分层存放，不得混写。
- 状态更新应可审计：关键写入、权限变更、批量操作、AI 写入和失败回滚必须记录必要上下文。
- 删除、覆盖、移动、批量修改和高风险 AI 操作必须先确认目标范围，无法确认时失败关闭。

## 安全与边界

- 文件读写、网络请求、服务启动、导入导出和外部工具调用必须处理错误，并限制资源占用。
- 网络请求必须有超时；批量请求必须限制并发和单次数量；流式数据必须及时释放。
- SQL 查询必须参数化；禁止拼接用户输入、块 ID、路径、搜索词或排除条件到 SQL 字符串。
- API Key、token、cookie、授权头和本地密钥不得在接口响应、日志、错误提示或计划文档中明文输出。
- AI 写入必须先生成可审阅变更，再由用户确认后正式提交；高风险或无法确定范围的操作必须拒绝或人工确认。
- 安全加固不得破坏笔记业务语义；对笔记 Block DOM、Markdown、用户 HTML 的处理必须优先保持既有内容结构。

## 错误处理

- 错误必须携带必要上下文：目标模块、操作类型、目标 ID 或安全裁剪后的路径、失败阶段和可恢复建议。
- 生产代码不得用占位实现、固定返回值或沉默失败伪装成功。
- 返回 `Result`、Promise、Go error 或等价错误值的调用必须显式处理、传播或记录；禁止盲目丢弃。
- 用户可见错误应清晰说明失败原因和下一步动作；内部日志应避免冗余刷屏并可按配置关闭调试输出。

## 测试与验证

- 新增逻辑必须在用户请求范围内补充对应测试；bug 修复优先补回归测试。
- 测试不得依赖真实外部服务；需要 AI、网络或第三方服务时使用 fake provider、mock 或本地夹具。
- 提交前按变更风险选择验证范围；跨模块、配置、安全、数据结构或用户工作流变更必须扩大验证。
- 不伪造测试结果；无法运行的验证必须说明原因、阻断点和已完成的替代检查。
- 文档规则、架构设计和实现状态发生冲突时，先记录冲突并请求确认；不得自动选择会改变架构方向的解释。

## Go 生产代码

- 生产代码禁止用 `panic` 处理业务错误；仅允许在初始化阶段遇到不可恢复的配置或环境错误时失败关闭，并必须保留清晰上下文。
- 所有 `error` 必须显式处理、包装上下文后向上传播或记录；禁止用 `_` 盲目丢弃错误返回值。
- 文件、网络、数据库、进程和长耗时操作必须支持超时或取消；跨调用链优先传递 `context.Context`。
- goroutine 必须有明确退出条件和资源释放路径；禁止无界并发，批量任务必须限制并发数和单次数量。
- 共享状态必须有明确所有权、锁边界和生命周期；新增并发读写路径必须避免数据竞争。
- 输入校验、路径归一化、权限检查和默认值补全应集中在边界层或公共 helper，避免在业务分支中重复散落。
- 新增 Go 逻辑必须补充对应测试；bug 修复优先补回归测试，并按影响范围运行相关 `go test`。
