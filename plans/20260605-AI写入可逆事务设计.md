# AI 写入可逆事务生产级设计

更新日期：2026-06-05

## 背景

用户明确要求 AI 写入必须先审阅并由用户主动选择写入方式，写入后还要支持撤回和取消撤回，避免 AI 破坏原笔记内容。

现有 AI 写入链路已经具备基础安全闭环：

- 写入型能力先生成 `patch/diff`，进入 patch review。
- 流式阶段使用 `ghost draft` 临时预览，不直接写真实块。
- 接受 patch 后通过后端 `/api/assistant/patch/apply` 统一写入。
- 后端会执行安全检查、目标归一化、当前笔记边界检查和实时原文校验。
- 前端本地 AI 操作历史已支持低风险回滚，但只覆盖追加/插入块和新建笔记，且存储在 localStorage。

当前缺口是：历史记录不是后端真相源，替换、删除、属性修改、重命名等操作没有完整反向事务，撤回后也没有统一的取消撤回能力。

## 目标

- 所有 AI 改写已有笔记内容的动作必须遵循：预览 -> 审阅 -> 接受 -> 后端写入 -> 后端审计。
- 每次成功写入必须生成可审计、可撤回、可取消撤回的后端历史记录。
- 撤回和取消撤回都必须经过后端安全边界、当前状态校验和原子写入，失败时不能部分提交。
- 只保存实现可逆性所必需的最小快照，不保存整篇无关笔记内容，不保存 API Key 或模型敏感信息。
- 多窗口、重启后仍能读取 AI 写入历史并执行撤回或取消撤回。
- 旧 localStorage 历史只作为兼容展示来源，不再作为生产级撤回真相源。

## 非目标

- 不把普通人工编辑全部纳入 AI 操作历史。
- 不改变普通编辑器 Ctrl+Z/Ctrl+Y 的既有行为。
- 不允许 AI 绕过 patch review 直接调用普通块/文件树写接口。
- 不在本阶段实现跨设备云同步审计表；后端本地持久化已满足单设备生产可逆要求。
- 不把模型请求正文、来源全文或密钥写入审计记录。

## 旧文档冲突处理

`plans/spec.md` 曾记录：用户显式保存 AI 生成新文档时，审计记录只保存目标、来源、摘要、session/profile 等元数据，不复制保存正文全文。

该口径与“写入之后还要支持撤回和取消撤回”存在冲突：如果撤回删除了 AI 新建笔记，取消撤回必须拥有重新创建该笔记的 forward snapshot。用户已在 2026-06-05 确认可逆写入方向，因此本设计以可逆事务为准：

- 改写已有笔记时，只保存受影响块/属性/标题的最小前后快照。
- AI 新建笔记或显式保存新文档如需支持取消撤回，必须保存该次 AI 生成 Markdown 的 forward snapshot。
- 不保存与该次 AI 写入无关的整篇工作空间内容或来源全文。

该冲突结论需要同步记录到 `plans/state.md`。

## 核心模型

### 状态

AI 操作历史状态统一为：

- `applied`：已写入，可撤回。
- `reverted`：已撤回，可取消撤回。
- `reapplied`：撤回后已重新应用，可再次撤回。
- `failed`：原始写入失败，仅可查看错误。
- `revert-failed`：撤回失败，保留原状态和错误。
- `reapply-failed`：取消撤回失败，保留原状态和错误。

### 后端历史记录

持久化文件：`storage/assistant_operation_history.json`

单条记录字段：

- `id`：历史记录 ID。
- `patchId` / `operationId` / `operationType`：来源 patch 与 operation 定位。
- `patch`：脱敏后的 patch 摘要和当前 operation，保留可读审阅信息。
- `status`：当前状态。
- `source` / `risk` / `sessionId` / `profileId`：来源和模型上下文元数据。
- `targetId` / `targetLabel` / `notebook` / `path`：目标定位。
- `snapshots`：最小可逆快照。
- `results`：写入结果，包含 applied target ID。
- `error`：失败原因。
- `createdAt` / `updatedAt`：时间戳。

持久化规则：

- 单文件 JSON 存储，机器读取使用 JSON。
- 写入时加进程内 mutex，使用临时文件安全写入。
- 默认保留最近 200 条，可作为常量集中定义。
- 损坏 JSON 不阻塞笔记编辑；读取失败返回空列表并记录错误，不自动覆盖损坏文件。

### 最小快照

每种 operation 的可逆信息：

| 类型 | 撤回 | 取消撤回 | 必要快照 |
| --- | --- | --- | --- |
| `append-note` | 删除本次追加生成的块 | 重新追加同样内容 | 新块 ID、父笔记 ID、after Markdown/DOM |
| `insert-after-block` | 删除本次插入生成的块 | 在原目标后重新插入 | 新块 ID、目标块 ID、after Markdown/DOM |
| `replace-selection` | 将目标块从 after 恢复为 before | 将目标块从 before 改回 after | 目标块 ID、before Markdown、after Markdown |
| `replace-block` | 将目标块从 after 恢复为 before | 将目标块从 before 改回 after | 目标块 ID、before Markdown、after Markdown |
| `delete-block` | 在原位置恢复被删块 | 再次删除该块 | 被删块 Markdown/DOM、父 ID、前后兄弟 ID、目标 ID |
| `rename-note` | 恢复旧标题 | 设置新标题 | note ID、old title、new title |
| `set-attrs` | 恢复旧属性值 | 重新设置新属性值 | 目标 ID、old attrs、new attrs |
| `create-note` / `create-child-note` | 删除 AI 创建的笔记 | 重新创建同样内容 | note ID、notebook、path、title、after Markdown |

撤回和取消撤回必须在执行前校验当前状态：

- 替换类操作：当前目标内容必须等于期望状态，否则拒绝，提示用户目标已被手动修改。
- 删除新增块：目标必须仍存在且属于原笔记范围，否则拒绝。
- 恢复删除块：原父块/笔记必须存在，原位置无法完全恢复时失败关闭，不自动猜测插入位置。
- 属性操作：当前涉及属性必须等于期望 after 或 before；不覆盖用户后续手动编辑。
- 重命名：当前标题必须等于期望标题；不覆盖用户后续手动改名。

## API 设计

### Patch Apply

扩展现有 `/api/assistant/patch/apply`：

- 请求新增 `audit` 元数据：`sessionId`、`profileId`、`targetLabel`。
- 成功写入后，后端生成历史记录。
- 响应新增 `historyId`，前端用它刷新历史 UI。
- 需要人工确认时不写历史。
- 写入失败时可记录 `failed` 历史，但不得包含正文快照。

### 历史列表

新增 `/api/assistant/history/list`

请求：

- `limit`：默认 20，最大 100。

响应：

- 后端历史记录列表，按 `updatedAt` 倒序。
- 记录内容可用于展示，但不暴露敏感配置或来源全文。

### 撤回

新增 `/api/assistant/history/revert`

请求：

- `id`：历史记录 ID。

行为：

- 只允许 `applied` 或 `reapplied` 状态撤回。
- 后端重新校验目标、当前状态和安全边界。
- 生成反向事务并提交。
- 成功后状态更新为 `reverted`。
- 失败后状态更新为 `revert-failed`，保留错误。

### 取消撤回

新增 `/api/assistant/history/reapply`

请求：

- `id`：历史记录 ID。

行为：

- 只允许 `reverted` 状态重新应用。
- 后端校验当前状态仍等于撤回后的期望状态。
- 生成正向事务并提交。
- 成功后状态更新为 `reapplied`。
- 失败后状态更新为 `reapply-failed`，保留错误。

## 前端行为

- Patch review 仍是唯一用户接受入口，按钮保留接受全部、接受单项、拒绝剩余、拒绝单项、复制补丁、继续调整。
- 写入成功后不再只写 localStorage 历史；前端从后端历史列表刷新。
- 历史面板展示：状态、来源、风险、目标、时间、错误、撤回/取消撤回按钮。
- `applied` / `reapplied` 显示“撤回”。
- `reverted` 显示“取消撤回”。
- `failed` / `revert-failed` / `reapply-failed` 只显示错误，不自动重试。
- 旧 localStorage 历史可以继续只读展示一段兼容期，但不能作为生产撤回入口。

## 安全与稳定性

- 撤回和取消撤回属于 AI 写入操作，必须继续经过 AI 安全内核。
- 硬禁止、黑名单或能力关闭时不得执行撤回/取消撤回。
- 状态校验失败时必须失败关闭，不覆盖用户后续手动编辑。
- 所有文件写入必须使用临时文件安全写入。
- 所有 Result 必须显式处理，Go 生产代码禁止新增 `panic!` 风格行为、`unwrap/expect` 不适用但仍遵守错误显式返回。
- 并发调用同一历史记录时必须串行化，避免重复撤回或重复重做。

## 验收标准

- AI 替换选区后，历史中显示“撤回”；撤回后内容恢复，历史显示“取消撤回”；取消撤回后内容再次变为 AI 结果。
- AI 追加/插入块后，撤回删除新块，取消撤回重新生成内容。
- AI 删除块后，撤回恢复原块，取消撤回再次删除。
- AI 重命名笔记后，撤回恢复旧标题，取消撤回恢复新标题。
- AI 设置属性后，撤回恢复旧属性，取消撤回恢复新属性。
- AI 新建笔记/显式保存新文档后，撤回删除该笔记，取消撤回重新创建同样内容。
- 如果用户在撤回前手动改过目标块/标题/属性，撤回失败并提示目标已变化。
- 重启应用后仍能看到后端历史并执行可逆操作。
- 前端目标测试、后端目标测试、`typecheck:app` 和 `git diff --check` 通过。

## 设计评审结论

本设计与现有 AI patch apply 架构一致，且把当前本地低风险回滚升级为后端持久可逆事务。主要风险是审计记录需要保存受影响内容快照；该风险通过最小快照、脱敏元数据、仅存 AI 写入相关内容和本地 `storage/` 持久化控制。

评审通过，可以进入代码落地阶段。
