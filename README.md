# SourceFlow

中文 | [English](README_EN.md)

问渠那得清如许，为有源头活水来。故名：源流 SourceFlow。

SourceFlow 是一个本地优先的智能笔记与知识工作空间。它保留了块编辑、双向链接、Markdown WYSIWYG 等成熟笔记体验，同时把 AI 一键处理、来源整理、同步保护、网页采集和插件生态接进日常写作流程。

如果你熟悉思源笔记，可以把 SourceFlow 理解为一个围绕“更顺手地写、整理、采集和沉淀”继续强化的版本。

- 当前仓库：[lonelyor/SourceFlow](https://github.com/lonelyor/SourceFlow)
- 许可证：`AGPLv3`
- 合规说明：见 [NOTICE.md](NOTICE.md)

## 为什么是 SourceFlow

- 原始项目：[思源笔记 SiYuan](https://github.com/siyuan-note/siyuan)

- 它不是把 AI 单独塞进一个聊天框，而是让 AI 围绕你正在写的笔记、当前选中的内容和刚导入的资料直接工作。
- 它强调本地优先和工作空间可控，尽量让数据、附件、同步目录、恢复入口和迁移过程都清晰可见。
- 它不只处理文本，还把网页、PDF、图片、代码和附件纳入同一条整理链路。
- 它允许扩展，但默认更克制，插件安装、来源、摘要和权限确认都尽量前置给用户。

## 功能特色

### 1. 围绕写作与整理设计的笔记空间

- 块式编辑、双向链接、面包屑、页签、分屏和上下文菜单这些基础能力都保留了下来，适合长期积累和重组内容。
- 保持 Markdown WYSIWYG 的直接编辑体验，不需要在“源码模式”和“预览模式”之间来回切换。
- 适合知识库、项目文档、研究笔记、个人记录和日常资料沉淀。
- PDF、闪卡、主题、导出等传统笔记能力依然可用，不会被 AI 工作流取代。

### 2. AI 直接服务于笔记，而不是停留在聊天

- 选中文本后就能直接做总结、提纲、润色、续写、问答和复习卡片，不需要复制粘贴到外部工具。
- AI 助手支持图片上传、拖拽和粘贴截图，适合边看资料边提问。
- AI 生成结果会集中进入成果侧栏，方便继续筛选、整理，再插回正式笔记。
- 对于高频操作，重点是“选中即用、生成即收口”，而不是增加新的学习成本。

### 3. 网页、PDF、图片和代码都能进入同一条来源链

- 公开网页可以直接通过 URL 导入，尽量转换成 Markdown 并把图片、附件本地化。
- 对于登录页、动态页和必须依赖浏览器上下文的页面，可以通过浏览器采集扩展保存当前页。
- 来源创作可以围绕文本、代码、PDF、图片等资料做整理、分析和写作。
- 图片 OCR、PDF 处理、附件归档和来源说明，可以让“资料”更快变成“可继续写的内容”。

### 4. 同步与恢复更谨慎，工作区更安全

- SourceFlow 支持 `本地文件系统`、`S3`、`WebDAV` 三种同步 provider，其中 `本地文件系统` 是默认 provider，不只是云端同步的备用选项。
- 它更强调“可观察的快照备份与恢复”，而不是黑盒式静默同步。
- 启动保护、离线继续编辑、同步诊断、冲突文档、数据历史和按时间点恢复都已经纳入同一套流程。
- 工作区、同步目录、数据仓库密钥和恢复描述文件都尽量保持明确，适合重视数据可迁移性和长期维护的人。

### 5. 可以扩展，但默认带边界

- 内置独立集市（Bazaar）体系，支持插件、主题等扩展内容。
- 插件安装和启用前会展示来源、摘要、`SHA-256` 和权限声明，不是“装完直接跑”。
- 插件默认安装后保持关闭，只有用户手动启用后才运行。
- 对于读取工作区、写入工作区、联网访问、宿主控制等高风险能力，会尽量用权限模型明确暴露。

### 6. 不只是一台电脑上的笔记

- 提供桌面端、移动端和 Docker 使用方式，适合个人设备、多端访问和自托管场景。
- 浏览器采集扩展可以把网页内容带回工作空间，而不是让资料长期散落在浏览器标签页里。
- Windows 便携包、桌面版和同步场景都已经纳入发布链路，适合日常长期使用。

## 浏览器采集扩展

SourceFlow 附带一个单独发布的浏览器采集扩展：`SourceFlow Page Saver`。

- 公开网页优先直接在 SourceFlow 里做 `URL 导入`，这样流程更短。
- 登录页、动态页、会员内容页，或者必须依赖浏览器上下文的页面，再使用这个扩展保存当前页。
- 扩展只负责读取当前浏览器里已经打开的页面内容，真正的 Markdown 转换、资源本地化和笔记写入仍由 SourceFlow 内核完成。
- 保存结果是 `Markdown + 本地 assets`，目标是“可继续整理和写作”，不是浏览器像素级归档，也不是 `MHTML`。

### 从 Releases 安装

每个 GitHub Releases 都会附带浏览器扩展压缩包：`sourceflow-page-saver-<version>.zip`。

1. 从 Releases 下载这个 zip 并解压。
2. 打开 Chrome 或 Edge 的扩展管理页。
3. 开启“开发者模式”。
4. 选择“加载已解压的扩展程序”。
5. 选择解压后的 `sourceflow-page-saver` 目录。

如果你只是本地调试，也可以直接加载源码目录：[browser-extension/sourceflow-web-clipper](browser-extension/sourceflow-web-clipper)。

## 同步与恢复备份

SourceFlow 当前支持 `本地文件系统`、`S3`、`WebDAV` 三种同步 provider。对于大多数自托管用户，我更推荐先从 `本地文件系统` 配起，因为它最直观、最好排查，也适合本机备份、移动硬盘、外接 SSD、已挂载 NAS 或映射网络盘这类“在系统里已经表现为本地目录”的场景。

### 先理解三个概念

- `工作空间` 是你平时实时编辑的本地目录。
- `同步目标` 是存放加密快照备份的目录或服务，不应该直接等同于工作空间本身。
- 即使选择的是 `本地文件系统`，界面里仍然会出现 `远端备份目录` 这个字段。它代表当前工作空间在该目标路径下使用的独立同步仓库名，默认是 `main`。

### 推荐配置步骤

1. 先在 `设置 -> 关于` 中初始化 `数据仓库密钥`。这个密钥用于同步数据的端到端加密；如果你是手动输入密码生成的，请牢记密码，同时把自动生成的 `backup-profile.json` 恢复描述文件妥善保存。
2. 打开 `设置 -> 同步与恢复备份`，选择同步 provider。
   `本地文件系统`：在 `Endpoint` 中填写一个已经存在的完整目录路径，建议使用独立备份目录，不要指向工作空间本身，也不要指向工作空间的父目录。便携模式下，位于便携根目录内的路径会按相对路径保存，位于外部的目录会按绝对路径保存。
   `S3`：填写 `Endpoint`、`Access Key`、`Secret Key`、`Bucket`、`Region` 等参数，具体值以你的对象存储服务商文档为准。
   `WebDAV`：填写 `Endpoint`、用户名和密码。它可以用，但性能和稳定性通常不如 `S3`，更适合作为兼容方案。
3. 设置 `远端备份目录`。如果你只有一个工作空间要同步，直接使用默认的 `main` 即可。一个本地工作空间应长期固定使用一个远端备份目录，不要来回切换；如果更换了 `数据仓库密钥`，也应该切换到新的备份目录。
4. 开启远端备份，并手动执行第一次同步。启用后建议立即点击一次同步按钮，先把当前工作空间备份上去。之后快照备份会在启动、退出、内容变更后延迟以及后台定时等时机自动执行，手动同步按钮也会一直保留。
5. 在第二台设备或新环境恢复时，优先使用空工作空间或新便携目录，然后导入 `backup-profile.json`，或者手动输入同一份 `数据仓库密钥`，并配置相同的 provider 与相同的 `远端备份目录`，再执行同步或恢复。

### 实用建议

- 建议开启 `同步冲突时生成冲突文档`，这样冲突发生时可以直接查看差异内容。
- 多设备经常同时在线时，可以开启 `同步感知`，让在线设备尽量更及时地收发同步信号。
- `同步间隔` 控制的是内容停止变化后的自动备份间隔，不是“每隔几秒强制全量重传”。
- 如果你导入了 `backup-profile.json`，但 `本地文件系统` 的备份目录已经移动，不需要手改文件；导入后重新选择当前目录即可。
- 不要把 `工作空间` 本身放在 OneDrive、Dropbox、iCloud 等第三方同步盘路径里。SourceFlow 会主动做这类风险检测并尽量阻止出问题。

## 插件系统现状

SourceFlow 已经具备插件系统和独立 Bazaar 集市机制，但当前版本还没有随 release 一起提供一批成熟的官方插件包。

- 宿主侧已经支持插件安装、ZIP 导入、来源记录、`SHA-256` 校验、权限声明和启用前确认。
- 仓库里目前提供的是用于自测和开发示例的插件：[examples/plugins/sourceflow-hello](examples/plugins/sourceflow-hello)。
- 对普通用户来说，可以把当前阶段理解为“插件框架已经具备，生态还在建设中”。
- 如果你愿意测试插件系统、提交反馈或自己编写插件，这部分能力已经可以开始用了。

## 当前平台状态

目前日常验证最充分的是 Windows 桌面端。

- Windows 是当前主要测试平台，也是我自己日常使用最多的环境。
- macOS、Linux、移动端和 Docker 相关能力在代码和构建链路里都保留了，但这一版还没有做同等强度的完整回归测试。
- 这个项目目前主要由我一个人持续维护，跨平台验证覆盖还不够。
- 如果你正在使用非 Windows 平台，欢迎帮我测试，并把系统版本、安装方式、复现步骤和日志反馈给我，这会非常有帮助。
